## Stack
- `backend/`: Node + Express + better-sqlite3 (SQLite), Port 3001. `frontend/`: React + Vite + Tailwind, Port 5173 (Proxy `/api`, `/uploads` und `/img` → 3001).
- Ein Docker-Image liefert Backend + gebautes Frontend aus. Server: IONOS-VPS, Caddy davor.
- UI-Texte, Kommentare, Commit-Nachrichten: **Deutsch**. Kommentare nur, wenn das *Warum* nicht offensichtlich ist.

## Lokal starten
```
cd backend  && npm install && npm run dev     # http://localhost:3001
cd frontend && npm install && npm run dev     # http://localhost:5173
```
Die Karten-Datenbank `backend/data.sqlite` (~45 MB) ist **nicht in Git**. Ohne sie gibt es keine Karten – eine Kopie von Justus dort hineinlegen. Nie Produktionsdaten oder `.env` committen.

## Deploy (WICHTIG)
**Jeder Push auf `main` deployt automatisch** (GitHub Actions → Server). Deshalb:
- Nur committen + pushen. **Nicht zusätzlich per SSH deployen** (doppelte Deploys → Fehler-Mails).
- Vorsicht bei Änderungen an Datenbank/Anmeldung: sie sind sofort live. Größeres lieber auf einem Branch bauen, testen, dann nach `main` mergen.
- Nach dem Push prüfen, ob der Lauf grün ist (`https://api.github.com/repos/juswilhes/mycardfolio/actions/runs?per_page=3`).

## Wichtige Regeln aus der Praxis
- **React-Falle:** nie `useEffect(load, [])`, wenn `load` ein Promise zurückgibt (React hält es für die Cleanup-Funktion → Blank Screen). Immer `useEffect(() => { load(); }, [])`.
- Nie ein Konto/Passwort für Anmeldungen benutzen oder Zugangsdaten eintragen; Tests, die einen Login brauchen, dem Nutzer überlassen.
- Sicherheit: Sitzungs-/Reset-Token liegen nur als SHA-256-Hash in der DB (`authService.js`); Kontosperre nach 5 Fehlversuchen.
- **Nachtlauf 1:00 Uhr (Europe/Berlin)**, `services/priceFetcher.js runDailyPriceJob`: (0) `variantFlags.js`: welche Ausführungen (normal/Reverse Holo/Holo) jede Karte hat (wenige Listenabfragen bei TCGdex); (1) `newCardsSync.js` sucht bei TCGdex neue Sets (nur wirklich neue, <7 Monate, kein Pocket) und neue Karten in Sets mit exakt gleicher ID und importiert sie über `services/tcgdexImport.js` (dasselbe nutzt `npm run import-tcgdex`); (2) Preise: zuerst alle Karten in einem Rutsch aus **Cardmarkets öffentlicher Tages-Preisliste** (`guidePrices.js` + `cardmarketGuide.js`, ca. 11 Sekunden statt ~20.000 Einzelabfragen), danach per Einzelabruf (TCGdex, Rückfall pokemontcg.io) nur noch die Karten, die sich dort nicht eindeutig zuordnen ließen; (3) Karten ohne Preis; (4) `analysisCache.js`: alle Auswertungen der Analyse neu rechnen + am Monatsersten den Monatsstand speichern; (5) `imageRepair.js`: fehlende/kaputte Kartenbilder -> Ersatz von scrydex (`images.scrydex.com/pokemon/<id>/small|large`), danach offizielle Pokémon-Datenbank (`assets.pokemon.com/.../web/<SET>/<SET>_EN_<Nr>.png`). **Achtung:** scrydex liefert für unbekannte Karten Status 200 + Platzhalter (Kartenrückseite, 45551/186316 Bytes) - Erkennung nur per HEAD mit `Accept-Encoding: identity` (sonst keine Content-Length). Vollprüfung aller Karten sonntags nachts und einmalig nach Logik-Änderungen (Marker `image_full_check_v2` in app_meta, bei Änderungen hochzählen); (6) Portfolio-Tagespunkt. Set-IDs unterscheiden sich je Quelle (unser `sv1` = TCGdex `sv01`): deshalb die Duplikat-Schutzregeln in newCardsSync.js nicht lockern.
- **Alles nur nachts um 1 Uhr (Justus):** Auch die Daten der Analyse (Booster vs. Top-Karten, Pull Rates, Wert pro Pack, Ziehen oder kaufen, Preisbewegungen) werden nur im Nachtlauf neu gerechnet und aus dem Speicher `services/analysisCache.js` ausgeliefert - nie bei jedem Seitenaufruf. Neue Analyse = Rechenfunktion in `BUILDERS` dort eintragen und im Endpunkt `analysis("name")` ausliefern. Ausnahme: Eingaben des Betreibers (Box-/Boosterpreise, Pull Rates) bauen den Speicher sofort neu, sonst sähe er sein Speichern nicht.
- **Wie der Preis entsteht (Justus: Trend allein und Tiefstpreis taugen nicht):** als "trend" wird der **Median aus Cardmarket-Trend, Ø 1 Tag, Ø 7 Tage und Ø 30 Tage** gespeichert (`robustPrice` in `priceProvider.js`, genutzt von `cardmarketRows` und `tcgdexImport.js`); höchster und niedrigster Wert fallen weg, bei weniger als drei Kennzahlen gilt der Trend. Grund: Bei Karten mit wenigen Verkäufen springt der Trend (Drowzee SV #210: 37 -> 80 EUR, Ø 30 Tage ruhig bei 47). Test an 132 Karten gegen TCGplayer: Median etwas näher als der Trend. Der Tiefstpreis (`low`) ist nie der Preis. **Grenze ±30 % um Ø 30 Tage** (`AVG30_BAND` in `robustPrice`, Justus 29.10.2026): bei dünnem Handel ziehen ein teurer Verkauf Trend und Ø 1 Tag gemeinsam hoch (Magikarp base6-52: 39 EUR bei Ø 30 = 10,55); Test an 1.073 Karten gegen TCGplayer gleich genau, aber keine Ausreißer mehr. Die gespeicherte Vergangenheit wurde einmalig genauso begrenzt (`capHistoryToAvg30Band`, Marker `price_band_history_v1`, läuft in Portionen im Hintergrund). **Gegenprobe für teure Karten** (`services/crossCheck.js`, Nachtlauf-Schritt "Gegenprobe", Justus: "Mittelwert aus Cardmarket und pokemontcg.io"): bei Karten ab **3 €** (Justus 23.10.2026, vorher 10 €) wird der Cardmarket-Wert (Median) mit dem TCGplayer-Marktpreis von pokemontcg.io (USA, USD -> EUR) gemittelt und ersetzt den heutigen "trend"-Wert (source bleibt cardmarket, damit die Reihe durchgeht); der TCGplayer-Wert liegt als `xcheck`-Zeile daneben (verhindert doppeltes Mitteln). Nur wenn die passende Ausführung bei TCGplayer existiert und der Wert höchstens 2,5x abweicht; sonst bleibt es beim Cardmarket-Wert. Ohne `POKEMONTCG_API_KEY` höchstens 800 Karten/Nacht, mit Schlüssel bis 12.000. **Einen Schlüssel gibt es nicht mehr** (dev.pokemontcg.io nimmt seit Okt 2026 keine Anmeldungen an, Nachfolger Scrydex kostet - Justus: kein Abo). Deshalb **reihum** (Justus 23.10.2026): zuerst nie geprüfte, dann die am längsten nicht geprüften Karten (bei Gleichstand die teureren), ~8.700 Karten ab 3 € = jede etwa alle 11 Nächte. Karten, die nicht dran sind, werden mit dem Wert der letzten ECHTEN Prüfung (Quelle `tcgplayer`, max. `CARRY_DAYS` = 14 Tage) gemittelt; der übernommene Wert steht mit Quelle `tcgplayer-vortag` daneben und zählt nicht als Prüfung (sonst rückt die Reihenfolge nicht weiter). So ist nichts im Wechsel gemittelt/ungemittelt; Preisbewegungen lassen Karten weg, deren Mitteln im Zeitraum begann oder endete. Wer die Formel ändert, zählt den Marker `guide_prices_v4` in `guidePrices.js` hoch, damit die Preise nach dem Deploy neu geschrieben werden.
- **Feste Cardmarket-Zuordnung + eine Quelle pro Reihe (Justus 23.10.2026, nach +/-99 %-Bewegungen):** Ursachen waren (a) TCGplayer-Ersatzwerte in derselben Reihe wie Cardmarket (Darkrai-EX bw5-107: 16 <-> 730 EUR), (b) der US-Ersatzpreis leerte `cards.cardmarket_product_id`, (c) die Korrektur der Produkt-Zuordnung änderte die gespeicherte Zuordnung und griff dadurch nur jede zweite Nacht (Gengar ecard3-10: 160 <-> 3371 EUR). Jetzt: `cards.cardmarket_pid_locked` = Produkt der ersten SICHEREN Zuordnung (`recordPrices` in `cardService.js`; sicher = eindeutig in Preisliste/Korrektur, nie geraten); fest zugeordnete Karten bepreist NUR die Preisliste mit ihrem Produkt (kein Einzelabruf, fehlt es: Tag bleibt leer); ein abweichender Vorschlag wird nur in `cardmarket_pid_conflict` notiert. Geratene Zuordnungen (ältestes passendes Produkt) werden nicht gespeichert. **Gleiche Karte zweimal im Set** (`pairIdenticalProducts` in `guidePrices.js`, Justus 29.10.2026: Pikachu Cosmic Eclipse #66 Common bekam das Produkt der #241 Secret Rare = 184 EUR): Cardmarket führt beide unter exakt demselben Namen. Zuordnung: gewöhnlichere Karte = günstigeres Produkt, aber nur Common < Uncommon < Rare < Rare Holo (darüber stimmt die Reihenfolge nicht, Special Illustration Rare oft teurer als Mega Hyper Rare); bleibt genau eine seltenere übrig, bekommt sie das letzte Produkt. Nur bei gleich vielen Produkten wie Karten, gleicher Reihenfolge nach Trend/Tiefstpreis/Ø30, mind. 1,5x Abstand und ohne TCGplayer-Widerspruch; überschreibt eine frühere feste Zuordnung (dann `price_valid_from` = heute). Mehr Produkte als Karten (Hala sm2-126: 3 Produkte) bleibt offen - Test an nur 1 prüfbaren Karte, zu wenig Beleg. **Einzelabruf:** ist das Produkt im Set geteilt und die Gegenprüfung bei pokemontcg.io nicht erreichbar, wird an dem Tag KEIN Wert geschrieben (`UNCHECKED` in `priceProvider.js`) - vorher abwechselnd richtiger und falscher Wert (Dark Gyarados base5-25: 21 <-> 392 EUR). TCGplayer-`trend` wird nicht geschrieben, wenn die Karte in den letzten 30 Tagen Cardmarket-Werte hat (Gegenprobe = `xcheck`, unberührt). Einmalig (Marker `price_wobbly_cleanup_v1`) bekamen Karten mit >=2 Sprüngen über Faktor 2,5 in 3 Wochen `price_valid_from` = Deploy-Zeit. **Preisbewegungen** (`moverFor` in `marketStats.js`): dieselbe Reihe wie Graph (`variantSeries`), aktueller Preis (= Kartenseite) gegen den Preis vor N Tagen (Startseite: **30 Tage**, Justus: größte Bewegungen des Monats, nicht des Tages), beide aus der geglätteten Reihe; Karten mit einem Tagessprung über Faktor 1,5 (+50 %) im Zeitraum + 7 Tage oder mit Zuordnungs-Abweichung fehlen, ebenso Karten, bei denen die Gegenprobe zuletzt einen Widerspruch zu TCGplayer über Faktor 2,5 fand (`xcheck_off`-Zeile, crossCheck.js). Offen: bei manchen Produkten ist schon Cardmarkets eigene Preisliste verzerrt (vermutlich bewertete Karten, z. B. Gengar & Mimikyu-GX sm9-53: Trend 599 bei Tiefstpreis 40).
- **Ein Preis, eine Reihe:** "Aktueller Preis" einer Karte = letzter Tageswert der Preisreihe, die der Graph zeigt (`latestTrend` in `cardService.js`); der 30-Tage-Schnitt (`avg30`) wird auf der Kartenseite NICHT mehr angezeigt (Justus 23.10.2026); die Veränderung (▲/▼ %) darunter gilt für den im Diagramm gewählten Zeitraum (1/3/6/12 Monate, `PriceSection.jsx` steuert den Zeitraum von `PriceChart`). Überall (Kartenseite, Sammlung, Set-Analyse) `latestTrend` nutzen, nie eigene Preisberechnungen - sonst weichen Zahl und Graph wieder voneinander ab. Euro-Formatierung nur über `frontend/src/lib/format.js`. **Ausführungen:** `cards.variant_flags` (aus TCGdex) entscheidet, ob eine Karte EINE oder ZWEI Preisreihen hat (`alignToPrintings` in `cardService.js`): Cardmarket liefert immer zwei Spalten, aber viele Karten (Illustration Rare, Rare Holo ...) gibt es nur in einer Ausführung. Eine Ausführung = eine Linie ohne Beschriftung (kein "Normal"). Zwei = Normal + Reverse Holo/Holo; ohne "normal" (ältere Rare Holo: Holo + Reverse Holo) heißt die erste Linie "Holo" (`baseLabel`). **Lücke bei TCGdex** (Justus 23.10.2026, Lapras sm11-36): für EX Delta Species bis Power Keepers und Black & White bis Cosmic Eclipse fehlen dort die Reverse Holos; `addMissingReverse` in `variantFlags.js` ergänzt sie für Common/Uncommon/Rare/Rare Holo, wenn TCGdex im Set (fast) keine Reverse Holos kennt, Cardmarket aber für mind. 80 % dieser Karten echte Angebote (Tiefstpreis) in der zweiten Spalte hat (Base Set/Neo/30th haben keine -> bleiben bei einer Ausführung). Cardmarkets zweite Spalte allein taugt nicht (auch ohne Reverse Holo mit Werten gefüllt). Marker `variant_flags_v2`. **Glättung** (`smooth` in `cardService.js`, Justus: Preise sprangen über Nacht um 15-25 %): nach dem Ausreißer-Filter wird jeder Tageswert zum Median aus sich und den zwei Vortagswerten (nur bei höchstens 4 Tagen Abstand); echte Preisänderungen zeigen sich so einen Tag später. Nur beim Lesen, gilt überall gleich (Graph, aktueller Preis, Sammlung, Portfolio, Preisbewegungen). **Ausreißer-Filter** (`despike` in `cardService.js`): ein Tageswert, der gegenüber dem Vortag um mehr als 40 % springt und am Folgetag wieder zurückfällt, wird beim Lesen durch den Vortag ersetzt (Rohdaten bleiben gespeichert); ein Sprung des jüngsten Tages zeigt bis zur Bestätigung in der nächsten Nacht den Vortagswert. Gilt für Graph, aktuellen Preis, Preisbewegungen und Portfolio gleichermaßen.
- Preise kommen über TCGdex (Cardmarket, EUR, **ein Wert pro Karte, weder nach Sprache noch nach Zustand getrennt** - Justus braucht aber eigentlich DE/EN je Near Mint; das ginge nur über die offizielle Cardmarket-API mit Zugang). **Antwort von Cardmarket Support (Okt 2026, David, Team Lead):** API-Zugang wird derzeit **niemandem** gewährt (keine Frist, auch nicht für Verkäufer); die öffentlichen Preis- und Produktlisten (price guide, product catalogue) dürfen **frei und nach Belieben genutzt** werden (schriftlich bestätigt - unsere Nutzung ist damit in Ordnung); Partner-/Affiliate-Programm nur nach Genehmigung, Ansprechpartnerin **Tracy Rutkowski, Head of Marketing** (auf Englisch, mit Projektdetails, Wartezeit mehrere Wochen). Deshalb DE/EN-Near-Mint-Preise vorerst nicht möglich: nicht erneut API oder CardTrader vorschlagen, solange sich daran nichts ändert. **Rückfallebene** für Karten ohne TCGdex-Preis (viele Promos): pokemontcg.io (`getRawPricesById` -> `pokemonTcgFallback` in `priceProvider.js`): zuerst deren Cardmarket-Wert (wenn höchstens 14 Tage alt), sonst TCGplayer-Marktpreis (USD -> EUR). Abrufe nacheinander mit Pause; ein kostenloser `POKEMONTCG_API_KEY` (dev.pokemontcg.io, in der `.env` des Servers) macht die Quelle schneller und zuverlässiger. **Gegenprüfung falscher Produkt-Zuordnung** (`correctSharedProduct` in `priceProvider.js`): zuerst wird das richtige Produkt in **Cardmarkets öffentlicher Tages-Preisliste** gesucht (`cardmarketGuide.js`, Dateien `price_guide_6.json` + `products_singles_6.json` unter downloads.s3.cardmarket.com; Produktname enthält die Angriffe, z. B. `Arceus Lv.100 [Water | Fastwave]`; Zuordnung über Name + Angriffsnamen, nur bei eindeutigem Treffer; Trainer/Energien ohne Angriffe sind so nicht lösbar) - frische Cardmarket-Werte; erst danach der Vergleich mit pokemontcg.io. TCGdex ordnet bei Karten mit gleichem Namen im selben Set manchmal allen dasselbe Cardmarket-Produkt zu (Ponyta Arceus Nr. 46/72 bekamen den Preis der SH11, ca. 1.800 Karten teilen sich ein Produkt). Teilt sich eine Karte ihr Produkt mit einer Karte desselben Sets und liegt der TCGdex-Trend mehr als 3x über dem TCGplayer-Marktpreis (pokemontcg.io), gelten stattdessen die Werte von pokemontcg.io; `cards.price_valid_from` blendet die älteren (falschen) Preise aus, der Cardmarket-Link entfällt. Jede Karte soll jede Nacht einen Preis bekommen (Justus: "wirklich ALLE"). **Preise werden NUR einmal täglich um 1:00 Uhr (Europe/Berlin) geholt** (`services/priceFetcher.js`: alle Karten, danach Karten ohne Preis) - nie beim Öffnen einer Seite, Hinzufügen oder Import (Seiten lesen nur aus der DB; sonst wird die Seite bei 20.000+ Karten langsam). Kein "Preis jetzt aktualisieren"-Button. Schwere Abfragen über alle Karten: korrelierte Teilabfragen je Karte (`CARD_CURRENT_PRICE_SQL`), nicht die View `card_price_avg30` joinen (blockiert den Server); Preisbewegungen sind 30 Min. gecacht. ## Sammlung: Variante zählt
- Jeder Sammlungseintrag hat eine Variante (Normal/Holo/Reverse Holo/1st Edition) und wird mit dem Preis **seiner** Variante bewertet (`latestTrend(card_id, variant)`, Portfolio-Verlauf und Bewegungen über `variantSeries` in `cardService.js`). Nie mit einem Preis pro Karte rechnen - Gruppen (mehrere Einträge einer Karte) summieren je Eintrag.

## Startseite & News
- **Start (`/`) ist eine eigene Seite** (Menüpunkt "Start", für alle); **"Meine Sammlung" liegt unter `/sammlung`** (nur mit Login; Menüpunkt "Sammlung", `id="nav-sammlung"` bleibt für die Animation). Links auf die Sammlung immer `/sammlung`, nie `/`. Neue feste Seite = auch in `STATIC_PATHS` (`middleware/hits.js`) und `PRIVATE_PAGES` (`seo.js`) eintragen. Angemeldet zeigt `Landing.jsx` (Variable `member`) oben das kleine Portfolio-Fenster (`components/PortfolioWindow.jsx`: Wert, Karten, Gewinn/Verlust, 30-Tage-Linie, Buttons) und lässt die Werbeteile weg (Pitch, So funktioniert's, Funktionen, FAQ, Schluss); die Zahlen-Kacheln (Karten/Sets/Preisstand) entfallen ebenfalls (Justus: Angemeldete brauchen sie nicht); Preisbewegungen, Booster-Check und Artikel bleiben.
- `/` zeigt abgemeldeten Besuchern die Landing-Page (`pages/Landing.jsx`): Zahlen, Preisbewegungen des Monats (30 Tage), Booster-Check (Top 3), Funktionen, neueste Artikel, FAQ. Die Daten kommen aus `GET /api/stats/landing` (nur aus den Nacht-Auswertungen) und `/api/articles`. Mehr Tiefe: Justus fragt im Chat nach, Claude recherchiert dort von Hand.
- **Sichtbarer Text für Suchmaschinen:** `services/seo.js` setzt je Seite Titel/Beschreibung (Stichwort "Wert & Preis"), strukturierte Daten (BreadcrumbList) und einen kurzen Text samt Links in `<div id="root">` (Karte: Wertsatz mit Preis und Stand; Set: die 10 wertvollsten Karten aus `analysis("setTopCards")` + Liste aller Karten; Start/Alle Karten: Links auf alle Sets). React ersetzt den Block beim Laden. Bei neuen öffentlichen Seitentypen dort einen Text ergänzen. Kein `Product`/`Offer`-Markup (wir verkaufen nichts - das würde Google als irreführend werten).

Reine Näherung - gut getarnte Roboter lassen sich nicht ausschließen.

Die Adresse aus der Produktnummer (`?idProduct=`) landet bei Cardmarket auf der Startseite - nie wieder so bauen. Ohne Treffer gibt `cardmarketLink()` eine Cardmarket-Suche nach dem Kartennamen als Ersatz, wenn möglich auf das Set der Karte beschränkt (`cards.cardmarket_expansion`, aus der Preisliste). Alle Links tragen `utm_source=mycardfolio` (Cardmarket soll uns als Quelle erkennen). Cardmarket blockt automatische Abrufe (Bot-Prüfung) - Links lassen sich nur im normalen Browser prüfen.

Die Suche stellt passende Karten nach oben (ganzer Name oder Anfang ab 4 Zeichen), Kartenseite zeigt "Bei Sammlern bekannt als", Titel/Beschreibung für Google beginnen mit dem Spitznamen (`seo.js`).

## Suchmaschinen (SEO)
- Die App ist eine SPA: Titel, Beschreibung, canonical, noindex und Vorschaubild setzt der **Server** pro Seite ein (`backend/src/services/seo.js`, der Block zwischen `<!--seo:start-->` und `<!--seo:end-->` in `frontend/index.html` wird ersetzt - Markierungen nicht entfernen). Neue öffentliche Seite = Eintrag in `PUBLIC_PAGES`/`metaFor`; Seiten nur für Angemeldete stehen in `PRIVATE_PAGES` (noindex).
- **Set-Adressen sind lesbar** (`/sets/mega-evolution` statt `/sets/me1`): Slug aus dem Set-Namen (`services/setSlugs.js`, bei gleichem Namen mit angehängter ID). Die API und die Seite nehmen Slug ODER ID; alte ID-Adressen leitet der Server per 301 um. Links auf Sets: `set.slug ?? set.id`.
- **Karten-Adressen sind lesbar** (`/database/arceus-60-cherubi` statt `/database/pl4-60`: Set-Slug + Nummer + Kartenname, `services/cardSlugs.js`). Die API (`/api/cards/external/:externalId`) und die Kartenseite nehmen Slug ODER ID, alte ID-Adressen leitet der Server per 301 um; die Kartenseite arbeitet nach dem Laden mit der echten ID (`card.external_id`). Links auf Karten: `cardPath(card)` aus `lib/paths.js` (nutzt `card.slug`, sonst die ID; Datenquellen, die Karten-Links liefern, hängen `slug` mit an).
- **Alte Adressen umleiten:** Google kennt noch Adressen aus der Zeit vor der neuen Seite (Search Console, 404-Bericht). Wer Klicks/Impressionen hatte, bekommt in `OLD_ARTICLE_PATHS` (`seo.js`, `redirectFor`) eine 301 auf einen passenden Artikel (nur solange der Artikel veröffentlicht ist). Bisher: `/die-besten-tipps-zur-bewertung-ihrer-trading-cards` -> Artikel "Wie finde ich heraus, was meine Pokémon-Karte wert ist?" (Marker `article_karte_wert_v1`, 18.10.2026; Ziel: Suchanfragen "wert", "preis", "was ist der wert der karte"). Nach dem Deploy gibt Justus in der Search Console beim 404-Bericht "Fehlerbehebung überprüfen" ein.
- `/sitemap.xml` wird dynamisch gebaut (feste Seiten, alle Sets, Karten, Illustratoren) und nachts im Nachtlauf neu erzeugt. Nicht gefundene Karten/Sets liefern echten 404.
- **`/api` nie in der robots.txt sperren:** Google rendert die Seiten und holt die Daten von dort.
- Google-Anmeldung (Search Console, Sitemap einreichen) kann nur Justus mit seinem Google-Konto machen.

## Analyse-Seite
- Der Reiter "Markt" wurde entfernt (`MarketMovers`/`SetsOverview` liegen ungenutzt im Code, falls daraus eigene Analysen werden sollen). Reihenfolge: Meine Sammlung zuerst.
- Nav-Punkt "Analyse" (`/analyse`, früher "Statistik"): Auswahl verschiedener Analysen. Neue Analyse = neuer Eintrag in `ANALYSES` in `frontend/src/pages/Stats.jsx` (+ Komponente, ggf. Endpunkt unter `/api/stats`). "Meine Sammlung" bleibt in jedem Fall erhalten. Umschalter = `SegmentedToggle` (gleich wie bei "Alle Karten").
- **Regel (Justus):** Alles, was zu einer Analyse gehört, steht NUR unter "Analyse" - nicht zusätzlich auf Set- oder Kartenseiten. Auch die Pflege der Daten (Betreiber-Ansicht) passiert dort.
- **Booster-/Displaypreise automatisch** (Justus 29.10.2026, `services/sealedPrices.js`, Nachtlauf-Schritt "Sealed-Preise"): aus Cardmarkets öffentlicher Liste `products_nonsingles_6.json` + derselben Preisliste. Einzelbooster = kürzester Name "<Set> Booster" (ohne Sleeved/Fun Pack/"(6 Cards)"), Display = "<Set> Booster Box" (nicht "(18 Boosters)" = halbes Display, nicht Enhanced/Case/Bundle); Display muss 10-80x Booster kosten, sonst bekommt das Set gar keinen automatischen Preis. Teilsets (Trainer Gallery, Shiny Vault) teilen die Erweiterung - Preis nur beim Set, dessen Name im Produktnamen steht. **Mittelwert mit TCGplayer** (Justus 29.10.2026: Cardmarkets Liste mittelt über alle Sprachen, englische Displays sind teurer - Mega Evolution 209 EUR vs. englisch ~280): Preis = (Cardmarket + TCGplayer-Marktpreis in EUR) / 2, wenn TCGplayer das Produkt hat und höchstens 2,5x abweicht, sonst Cardmarket allein. TCGplayer-Daten von **tcgcsv.com** (freier Tagesabzug der TCGplayer-Daten, Regeln https://tcgcsv.com/docs: eigener User-Agent `mycardfolio/1.0`, einmal pro Nacht, Pause zwischen Abrufen, nie aus dem Browser); TCGplayer-Gruppe über den Set-Namen ohne Kürzel ("SV02: ", "SM - ", "EX "), Sonderfälle in `TCG_GROUP_ALIAS`. Gespeichert in `card_sets.auto_*` (Einzelwerte in `auto_*_cm_cents`/`auto_*_tcg_cents`, die Rubrik "Sealed" zeigt beide). **Welcher Preis gilt** (`EFFECTIVE_SET_PRICES` in `services/setPrices.js`, überall in den Analysen): der automatische; hat der Betreiber in der Analyse selbst einen eingetragen (`manual_prices_override = 1`), seiner; beide Felder leer speichern = wieder automatisch. Anzeige: **auf der Set-Seite ganz oben über den Einzelkarten** (Justus 29.10.2026, `components/SealedPrices.jsx`, Daten als `sealed` in `GET /api/sets/:id`, `sealedForSet`; Links = Cardmarket-Suche nach dem Produktnamen) - KEINE eigene Rubrik unter "Alle Karten" mehr. Dazu je ein Produktbild von TCGplayer (`auto_booster_image`/`auto_box_image`, 400 px, über den Bild-Umweg, weißer Hintergrund wird dabei entfernt - `withoutWhiteBackground`/`TRANSPARENT_HOSTS` in `imageProxy.js`, Justus 29.10.2026; Host in `IMAGE_HOSTS`, Datenschutz Ziff. 8, freigegeben 29.10.2026). Angezeigt werden NUR Bild und Zahlen (Booster, Display, Stand), keine Erklärung der Berechnung und keine Einzelwerte der Quellen (Justus 29.10.2026: "ich will Fakten liefern"). Monatsstand des laufenden Monats wird jetzt jede Nacht aktualisiert.
- "Booster vs. Top-Karten" (früher "Display & Booster"): Box-/Boosterpreise siehe oben (automatisch, eigene Eingabe in der Analyse geht vor, `PATCH /api/sets/:id/prices`); Sondersets ohne Display (30th Celebration, Black Bolt) haben nur einen Boosterpreis. Klick auf ein Set zeigt die 20 teuersten Karten. Über der Tabelle ein Balkendiagramm (`ValueBars`, Justus 30.10.2026): je Set Displaypreis neben Wert der Top 20, Reihenfolge wie die Tabelle, erst 12 Sets, dann "alle anzeigen"; nur Sets mit Display. Verlauf: Tabelle `set_value_snapshots`, ein Stand je Set und Monat, geschrieben vom Nachtlauf am Monatsersten (1 Uhr), beim Serverstart nachgeholt und bei Preisänderung für den laufenden Monat aktualisiert (`services/setValueSnapshots.js`).
- "Wert pro Pack": erwarteter Wert eines Boosters aus Pull Rates x aktuelle Kartenpreise (`getPackValueAnalysis` in `marketStats.js`), Display = 36 Booster; Common/Uncommon/Rare nicht eingerechnet (keine Pull Rates), daher Untergrenze. Boosterpreise kommen aus "Booster vs. Top-Karten".
- "Set-Rangliste": ALLE Sets mit Booster- oder Displaypreis (Justus 29.10.2026), Spalten Hit Rate, Wert pro Pack, Booster, Display, Top-20-Wert, sortierbar; ohne Pull Rates bleiben Hit Rate/Wert pro Pack leer. "Wert pro Pack" und "Ziehen oder kaufen" zeigen nur Sets mit Pull Rates; setzt die fertigen Auswertungen zusammen (`buildSetRanking` in `marketStats.js`, abgeleiteter Eintrag `DERIVED` in `analysisCache.js`).
- "Ziehen oder kaufen": je Set die Chase-Karten (Seltenheiten mit Quote pro Karte) mit Preis; erwartete Packs = Quote, Kosten = Packs x Boosterpreis, Vergleich mit dem Kaufpreis (`getPullOrBuy` in `marketStats.js`, Rechnung im Frontend).
- "Pull Rates": Matrix Seltenheit x Set, Daten von Hand (`pull_rates`, `PATCH /api/sets/:id/pull-rates`), Pflege über "Pull Rates pflegen" in der Analyse. Die Hit Rate (Chance auf mind. 1 besondere Karte pro Pack) wird in `marketStats.js` berechnet. Sets, die in fremden Boostern stecken (Classic Collection -> 30th Celebration), stehen in `BOOSTER_OF` und erscheinen in den Analysen nicht als eigene Spalte, sondern zählen zum Booster-Set.
