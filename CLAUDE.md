# mycardfolio – Projektregeln für Claude

Pokémon-TCG-Sammlungstracker, live unter https://mycardfolio.de. Betreiber: Justus (spricht Deutsch, technisch kein Profi – **kurz und verständlich antworten**, bei Ops-Schritten erklären, *warum*).

## Stack
- `backend/`: Node + Express + better-sqlite3 (SQLite), Port 3001. `frontend/`: React + Vite + Tailwind, Port 5173 (Proxy `/api` und `/uploads` → 3001).
- Ein Docker-Image liefert Backend + gebautes Frontend aus. Server: IONOS-VPS, Caddy davor.
- UI-Texte, Kommentare, Commit-Nachrichten: **Deutsch**. Kommentare nur, wenn das *Warum* nicht offensichtlich ist.

## Lokal starten
```
cd backend  && npm install && npm run dev     # http://localhost:3001
cd frontend && npm install && npm run dev     # http://localhost:5173
```
Die Karten-Datenbank `backend/data.sqlite` (~45 MB) ist **nicht in Git**. Ohne sie gibt es keine Karten – eine Kopie von Justus dort hineinlegen. Nie Produktionsdaten oder `.env` committen.

## Deploy (WICHTIG)
**Jeder Push auf `main` deployt automatisch** (GitHub Actions → Server). Deshalb:
- Nur committen + pushen. **Nicht zusätzlich per SSH deployen** (doppelte Deploys → Fehler-Mails).
- Vorsicht bei Änderungen an Datenbank/Anmeldung: sie sind sofort live. Größeres lieber auf einem Branch bauen, testen, dann nach `main` mergen.
- Nach dem Push prüfen, ob der Lauf grün ist (`https://api.github.com/repos/juswilhes/mycardfolio/actions/runs?per_page=3`).

## Wichtige Regeln aus der Praxis
- **React-Falle:** nie `useEffect(load, [])`, wenn `load` ein Promise zurückgibt (React hält es für die Cleanup-Funktion → Blank Screen). Immer `useEffect(() => { load(); }, [])`.
- Nie ein Konto/Passwort für Anmeldungen benutzen oder Zugangsdaten eintragen; Tests, die einen Login brauchen, dem Nutzer überlassen.
- Sicherheit: Sitzungs-/Reset-Token liegen nur als SHA-256-Hash in der DB (`authService.js`); Kontosperre nach 5 Fehlversuchen.
- **Nachtlauf 1:00 Uhr (Europe/Berlin)**, `services/priceFetcher.js runDailyPriceJob`: (0) `variantFlags.js`: welche Ausführungen (normal/Reverse Holo/Holo) jede Karte hat (wenige Listenabfragen bei TCGdex); (1) `newCardsSync.js` sucht bei TCGdex neue Sets (nur wirklich neue, <7 Monate, kein Pocket) und neue Karten in Sets mit exakt gleicher ID und importiert sie über `services/tcgdexImport.js` (dasselbe nutzt `npm run import-tcgdex`); (2) Preise: zuerst alle Karten in einem Rutsch aus **Cardmarkets öffentlicher Tages-Preisliste** (`guidePrices.js` + `cardmarketGuide.js`, ca. 11 Sekunden statt ~20.000 Einzelabfragen), danach per Einzelabruf (TCGdex, Rückfall pokemontcg.io) nur noch die Karten, die sich dort nicht eindeutig zuordnen ließen; (3) Karten ohne Preis; (4) `analysisCache.js`: alle Auswertungen der Analyse neu rechnen + am Monatsersten den Monatsstand speichern; (5) `imageRepair.js`: fehlende/kaputte Kartenbilder -> Ersatz von scrydex (`images.scrydex.com/pokemon/<id>/small|large`), danach offizielle Pokémon-Datenbank (`assets.pokemon.com/.../web/<SET>/<SET>_EN_<Nr>.png`). **Achtung:** scrydex liefert für unbekannte Karten Status 200 + Platzhalter (Kartenrückseite, 45551/186316 Bytes) - Erkennung nur per HEAD mit `Accept-Encoding: identity` (sonst keine Content-Length). Vollprüfung aller Karten sonntags nachts und einmalig nach Logik-Änderungen (Marker `image_full_check_v2` in app_meta, bei Änderungen hochzählen); (6) Portfolio-Tagespunkt. Set-IDs unterscheiden sich je Quelle (unser `sv1` = TCGdex `sv01`): deshalb die Duplikat-Schutzregeln in newCardsSync.js nicht lockern.
- **Alles nur nachts um 1 Uhr (Justus):** Auch die Daten der Analyse (Booster vs. Top-Karten, Pull Rates, Wert pro Pack, Ziehen oder kaufen, Preisbewegungen) werden nur im Nachtlauf neu gerechnet und aus dem Speicher `services/analysisCache.js` ausgeliefert - nie bei jedem Seitenaufruf. Neue Analyse = Rechenfunktion in `BUILDERS` dort eintragen und im Endpunkt `analysis("name")` ausliefern. Ausnahme: Eingaben des Betreibers (Box-/Boosterpreise, Pull Rates) bauen den Speicher sofort neu, sonst sähe er sein Speichern nicht.
- **Wie der Preis entsteht (Justus: Trend allein und Tiefstpreis taugen nicht):** als "trend" wird der **Median aus Cardmarket-Trend, Ø 1 Tag, Ø 7 Tage und Ø 30 Tage** gespeichert (`robustPrice` in `priceProvider.js`, genutzt von `cardmarketRows` und `tcgdexImport.js`); höchster und niedrigster Wert fallen weg, bei weniger als drei Kennzahlen gilt der Trend. Grund: Bei Karten mit wenigen Verkäufen springt der Trend (Drowzee SV #210: 37 -> 80 EUR, Ø 30 Tage ruhig bei 47). Test an 132 Karten gegen TCGplayer: Median etwas näher als der Trend. Der Tiefstpreis (`low`) ist nie der Preis. **Gegenprobe für teure Karten** (`services/crossCheck.js`, Nachtlauf-Schritt "Gegenprobe", Justus: "Mittelwert aus Cardmarket und pokemontcg.io"): bei Karten ab 10 € wird der Cardmarket-Wert (Median) mit dem TCGplayer-Marktpreis von pokemontcg.io (USA, USD -> EUR) gemittelt und ersetzt den heutigen "trend"-Wert (source bleibt cardmarket, damit die Reihe durchgeht); der TCGplayer-Wert liegt als `xcheck`-Zeile daneben (verhindert doppeltes Mitteln). Nur wenn die passende Ausführung bei TCGplayer existiert und der Wert höchstens 2,5x abweicht; sonst bleibt es beim Cardmarket-Wert. Ohne `POKEMONTCG_API_KEY` höchstens 800 Karten/Nacht (die teuersten zuerst), mit Schlüssel bis 4000. Wer die Formel ändert, zählt den Marker `guide_prices_v3` in `guidePrices.js` hoch, damit die Preise nach dem Deploy neu geschrieben werden.
- **Ein Preis, eine Reihe:** "Aktueller Preis" einer Karte = letzter Tageswert der Preisreihe, die der Graph zeigt (`latestTrend` in `cardService.js`); der 30-Tage-Schnitt (`avg30`) ist nur Zusatzinfo darunter, nie die Hauptzahl. Überall (Kartenseite, Sammlung, Set-Analyse) `latestTrend` nutzen, nie eigene Preisberechnungen - sonst weichen Zahl und Graph wieder voneinander ab. Euro-Formatierung nur über `frontend/src/lib/format.js`. **Ausführungen:** `cards.variant_flags` (aus TCGdex) entscheidet, ob eine Karte EINE oder ZWEI Preisreihen hat (`alignToPrintings` in `cardService.js`): Cardmarket liefert immer zwei Spalten, aber viele Karten (Illustration Rare, Rare Holo ...) gibt es nur in einer Ausführung. Eine Ausführung = eine Linie ohne Beschriftung (kein "Normal"). Zwei = Normal + Reverse Holo/Holo; ohne "normal" (ältere Rare Holo: Holo + Reverse Holo) heißt die erste Linie "Holo" (`baseLabel`). **Glättung** (`smooth` in `cardService.js`, Justus: Preise sprangen über Nacht um 15-25 %): nach dem Ausreißer-Filter wird jeder Tageswert zum Median aus sich und den zwei Vortagswerten (nur bei höchstens 4 Tagen Abstand); echte Preisänderungen zeigen sich so einen Tag später. Nur beim Lesen, gilt überall gleich (Graph, aktueller Preis, Sammlung, Portfolio, Preisbewegungen). **Ausreißer-Filter** (`despike` in `cardService.js`): ein Tageswert, der gegenüber dem Vortag um mehr als 40 % springt und am Folgetag wieder zurückfällt, wird beim Lesen durch den Vortag ersetzt (Rohdaten bleiben gespeichert); ein Sprung des jüngsten Tages zeigt bis zur Bestätigung in der nächsten Nacht den Vortagswert. Gilt für Graph, aktuellen Preis, Preisbewegungen und Portfolio gleichermaßen.
- Preise kommen über TCGdex (Cardmarket, EUR, **ein Wert pro Karte, weder nach Sprache noch nach Zustand getrennt** - Justus braucht aber eigentlich DE/EN je Near Mint; das ginge nur über die offizielle Cardmarket-API mit Zugang). **Rückfallebene** für Karten ohne TCGdex-Preis (viele Promos): pokemontcg.io (`getRawPricesById` -> `pokemonTcgFallback` in `priceProvider.js`): zuerst deren Cardmarket-Wert (wenn höchstens 14 Tage alt), sonst TCGplayer-Marktpreis (USD -> EUR). Abrufe nacheinander mit Pause; ein kostenloser `POKEMONTCG_API_KEY` (dev.pokemontcg.io, in der `.env` des Servers) macht die Quelle schneller und zuverlässiger. **Gegenprüfung falscher Produkt-Zuordnung** (`correctSharedProduct` in `priceProvider.js`): zuerst wird das richtige Produkt in **Cardmarkets öffentlicher Tages-Preisliste** gesucht (`cardmarketGuide.js`, Dateien `price_guide_6.json` + `products_singles_6.json` unter downloads.s3.cardmarket.com; Produktname enthält die Angriffe, z. B. `Arceus Lv.100 [Water | Fastwave]`; Zuordnung über Name + Angriffsnamen, nur bei eindeutigem Treffer; Trainer/Energien ohne Angriffe sind so nicht lösbar) - frische Cardmarket-Werte; erst danach der Vergleich mit pokemontcg.io. TCGdex ordnet bei Karten mit gleichem Namen im selben Set manchmal allen dasselbe Cardmarket-Produkt zu (Ponyta Arceus Nr. 46/72 bekamen den Preis der SH11, ca. 1.800 Karten teilen sich ein Produkt). Teilt sich eine Karte ihr Produkt mit einer Karte desselben Sets und liegt der TCGdex-Trend mehr als 3x über dem TCGplayer-Marktpreis (pokemontcg.io), gelten stattdessen die Werte von pokemontcg.io; `cards.price_valid_from` blendet die älteren (falschen) Preise aus, der Cardmarket-Link entfällt. Jede Karte soll jede Nacht einen Preis bekommen (Justus: "wirklich ALLE"). **Preise werden NUR einmal täglich um 1:00 Uhr (Europe/Berlin) geholt** (`services/priceFetcher.js`: alle Karten, danach Karten ohne Preis) - nie beim Öffnen einer Seite, Hinzufügen oder Import (Seiten lesen nur aus der DB; sonst wird die Seite bei 20.000+ Karten langsam). Kein "Preis jetzt aktualisieren"-Button. Schwere Abfragen über alle Karten: korrelierte Teilabfragen je Karte (`CARD_CURRENT_PRICE_SQL`), nicht die View `card_price_avg30` joinen (blockiert den Server); Preisbewegungen sind 30 Min. gecacht. Neue Sets: `npm run import-tcgdex -- <setId>`.
- Rechtstexte (`frontend/src/lib/legal.js`, `LEGAL_REVIEWED=false`) sind Entwürfe und noch nicht anwaltlich geprüft – Banner nicht entfernen.

Links auf die Sammlung immer `/sammlung`, nie `/`. Neue feste Seite = auch in `STATIC_PATHS` (`middleware/hits.js`) und `PRIVATE_PAGES` (`seo.js`) eintragen. Angemeldet zeigt `Landing.jsx` (Variable `member`) oben das kleine Portfolio-Fenster (`components/PortfolioWindow.jsx`: Wert, Karten, Gewinn/Verlust, 30-Tage-Linie, Buttons) und lässt die Werbeteile weg (Pitch, So funktioniert's, Funktionen, FAQ, Schluss); die Zahlen-Kacheln (Karten/Sets/Preisstand) entfallen ebenfalls (Justus: Angemeldete brauchen sie nicht); Preisbewegungen, Booster-Check und Artikel bleiben.

Die Daten kommen aus `GET /api/stats/landing` (nur aus den Nacht-Auswertungen) und `/api/articles`. Reihenfolge: Einstieg, Zahlen, So funktioniert's, Preisbewegungen, Booster-Check, Funktionen (Vektorsymbole), Artikel, FAQ. Tonfall: locker, mit wenigen Pokémon-Anspielungen (nicht übertreiben, die Seite soll seriös bleiben).
- **News & Artikel** (`/news`, `/news/:slug`): nur eigene Texte des Betreibers, keine Fremdinhalte (Lizenzfrage von PokeBeach & Co. umgangen). Tabelle `articles`, Schreiben/Bearbeiten/Löschen nur Betreiber direkt auf der Seite (`ArticleEditor`), Entwürfe nur für ihn sichtbar. Textformat: `##` Überschrift, `-` Liste, `>` Zitat, `**fett**`, `[Text](Ziel)` (`components/Prose.jsx`). Drei Startartikel legt `seedStarterArticles` einmalig an (Marker `articles_seeded_v1`). **Weitere Artikel per Deploy veröffentlichen** (Claude hat keinen Zugriff auf die Server-Datenbank): Eintrag in `services/articleSeedsLater.js` (eigener `marker`, `slug`, `image` unter `/news/...` aus `frontend/public/news/`), `seedLaterArticles` legt ihn beim Start genau einmal an (gelöscht = bleibt weg). Danach bearbeitet Justus ihn im Editor; spätere Änderungen an der Seed-Datei wirken NICHT auf den schon angelegten Artikel. **Jeder Artikel hat ein Titelbild** (`articles.image`): eigener Upload des Betreibers (`POST /api/articles/image`, Ordner `uploads/news`, max. 5 MB) oder das Standardbild; mitgelieferte Vektor-Titelbilder liegen in `frontend/public/news/`. Link-Vorschauen können kein SVG - dort fällt das Vorschaubild auf das Logo zurück. Artikel stehen in der Sitemap und haben eigene Meta-Tags (`seo.js`).

## Cardmarket-Link
- **Tagesbericht-Mail** (`npm run report`, `scripts/dailyReport.js`): Kennzahlen + Abschnitt "Anregungen für die News-Seite" aus frei abrufbaren Feeds (`services/communityTopics.js`: Pokezentrum-News, PokéBeach-Forum, Reddit r/PokemonTCG; best effort, Reddit drosselt Server). **Kein X/Instagram/TikTok** (nicht erreichbar bzw. kostenpflichtig) und **keine KI-Zusammenfassung** - Justus will keine laufenden Zusatzkosten (Anthropic-API abgelehnt). Mehr Tiefe: Justus fragt im Chat nach, Claude recherchiert dort von Hand.
- **Sichtbarer Text für Suchmaschinen:** `services/seo.js` setzt je Seite Titel/Beschreibung (Stichwort "Wert & Preis"), strukturierte Daten (BreadcrumbList) und einen kurzen Text samt Links in `<div id="root">` (Karte: Wertsatz mit Preis und Stand; Set: die 10 wertvollsten Karten aus `analysis("setTopCards")` + Liste aller Karten; Start/Alle Karten: Links auf alle Sets). React ersetzt den Block beim Laden. Bei neuen öffentlichen Seitentypen dort einen Text ergänzen. Kein `Product`/`Offer`-Markup (wir verkaufen nichts - das würde Google als irreführend werten).
- **Besucherzählung "menschlich"** (Tagesbericht-Mail): `middleware/hits.js` zählt Besucher nur ohne erkannte Roboter (Browserkennung `BOT_UA`, wird nicht gespeichert; Roboter-Aufrufe getrennt als `bot_hits`); "menschlich" = zusätzlich hat das Frontend (`App.jsx`, erste Interaktion: scrollen/klicken/tippen, nicht bei `navigator.webdriver`) `POST /api/ping` gemeldet (`daily_humans`, nur Hash, 7 Tage). Reine Näherung - gut getarnte Roboter lassen sich nicht ausschließen.
- "Auf Cardmarket ansehen" führt auf die **genaue Karte**: die echte Adresse (`.../Singles/Scarlet-Violet/Drowzee-V2-SVI210`) steht in `cards.cardmarket_page` und wird von `services/cardmarketLinks.js` über pokemontcg.io (`prices.pokemontcg.io/cardmarket/<id>`, Weiterleitung) ermittelt: einmal im Hintergrund nach dem Deploy, danach im Nachtlauf für neue Karten (sonntags auch die bisher unbekannten). Die Adresse aus der Produktnummer (`?idProduct=`) landet bei Cardmarket auf der Startseite - nie wieder so bauen. Ohne Treffer gibt `cardmarketLink()` eine Cardmarket-Suche nach dem Kartennamen als Ersatz, wenn möglich auf das Set der Karte beschränkt (`cards.cardmarket_expansion`, aus der Preisliste). Alle Links tragen `utm_source=mycardfolio` (Cardmarket soll uns als Quelle erkennen). Cardmarket blockt automatische Abrufe (Bot-Prüfung) - Links lassen sich nur im normalen Browser prüfen.

## Kartensuche
- "Alle Karten": Suchfeld findet Karten UND Sets (passende Sets stehen über den Karten); Auswahl "Kartenart" filtert nach `cards.subtypes` (LV.X = "Level-Up", ex, GX, V, VMAX, Unterstützer ...), auch ohne Suchtext (`GET /api/cards/search?q=&type=`, Liste der Arten `GET /api/cards/types` aus dem Analyse-Speicher).

## Suchmaschinen (SEO)
- Die App ist eine SPA: Titel, Beschreibung, canonical, noindex und Vorschaubild setzt der **Server** pro Seite ein (`backend/src/services/seo.js`, der Block zwischen `<!--seo:start-->` und `<!--seo:end-->` in `frontend/index.html` wird ersetzt - Markierungen nicht entfernen). Neue öffentliche Seite = Eintrag in `PUBLIC_PAGES`/`metaFor`; Seiten nur für Angemeldete stehen in `PRIVATE_PAGES` (noindex).
- **Set-Adressen sind lesbar** (`/sets/mega-evolution` statt `/sets/me1`): Slug aus dem Set-Namen (`services/setSlugs.js`, bei gleichem Namen mit angehängter ID). Die API und die Seite nehmen Slug ODER ID; alte ID-Adressen leitet der Server per 301 um. Links auf Sets: `set.slug ?? set.id`.
- **Karten-Adressen sind lesbar** (`/database/arceus-60-cherubi` statt `/database/pl4-60`: Set-Slug + Nummer + Kartenname, `services/cardSlugs.js`). Die API (`/api/cards/external/:externalId`) und die Kartenseite nehmen Slug ODER ID, alte ID-Adressen leitet der Server per 301 um; die Kartenseite arbeitet nach dem Laden mit der echten ID (`card.external_id`). Links auf Karten: `cardPath(card)` aus `lib/paths.js` (nutzt `card.slug`, sonst die ID; Datenquellen, die Karten-Links liefern, hängen `slug` mit an).
- `/sitemap.xml` wird dynamisch gebaut (feste Seiten, alle Sets, Karten, Illustratoren) und nachts im Nachtlauf neu erzeugt. Nicht gefundene Karten/Sets liefern echten 404.
- **`/api` nie in der robots.txt sperren:** Google rendert die Seiten und holt die Daten von dort.
- Google-Anmeldung (Search Console, Sitemap einreichen) kann nur Justus mit seinem Google-Konto machen.

## Analyse-Seite
- Der Reiter "Markt" wurde entfernt (`MarketMovers`/`SetsOverview` liegen ungenutzt im Code, falls daraus eigene Analysen werden sollen). Reihenfolge: Meine Sammlung zuerst.
- Nav-Punkt "Analyse" (`/analyse`, früher "Statistik"): Auswahl verschiedener Analysen. Neue Analyse = neuer Eintrag in `ANALYSES` in `frontend/src/pages/Stats.jsx` (+ Komponente, ggf. Endpunkt unter `/api/stats`). "Meine Sammlung" bleibt in jedem Fall erhalten. Umschalter = `SegmentedToggle` (gleich wie bei "Alle Karten").
- **Regel (Justus):** Alles, was zu einer Analyse gehört, steht NUR unter "Analyse" - nicht zusätzlich auf Set- oder Kartenseiten. Auch die Pflege der Daten (Betreiber-Ansicht) passiert dort.
- "Booster vs. Top-Karten" (früher "Display & Booster"): Box-/Boosterpreis pro Set pflegt der Betreiber von Hand in der Analyse (`PATCH /api/sets/:id/prices`); Sondersets ohne Display (30th Celebration, Black Bolt) haben nur einen Boosterpreis. Klick auf ein Set zeigt die 20 teuersten Karten. Verlauf: Tabelle `set_value_snapshots`, ein Stand je Set und Monat, geschrieben vom Nachtlauf am Monatsersten (1 Uhr), beim Serverstart nachgeholt und bei Preisänderung für den laufenden Monat aktualisiert (`services/setValueSnapshots.js`).
- "Wert pro Pack": erwarteter Wert eines Boosters aus Pull Rates x aktuelle Kartenpreise (`getPackValueAnalysis` in `marketStats.js`), Display = 36 Booster; Common/Uncommon/Rare nicht eingerechnet (keine Pull Rates), daher Untergrenze. Boosterpreise kommen aus "Booster vs. Top-Karten".
- "Set-Rangliste": Hit Rate, Wert pro Pack und Top-20-Wert je Set in einer sortierbaren Tabelle; setzt die fertigen Auswertungen zusammen (`buildSetRanking` in `marketStats.js`, abgeleiteter Eintrag `DERIVED` in `analysisCache.js`).
- "Ziehen oder kaufen": je Set die Chase-Karten (Seltenheiten mit Quote pro Karte) mit Preis; erwartete Packs = Quote, Kosten = Packs x Boosterpreis, Vergleich mit dem Kaufpreis (`getPullOrBuy` in `marketStats.js`, Rechnung im Frontend).
- "Pull Rates": Matrix Seltenheit x Set, Daten von Hand (`pull_rates`, `PATCH /api/sets/:id/pull-rates`), Pflege über "Pull Rates pflegen" in der Analyse. Die Hit Rate (Chance auf mind. 1 besondere Karte pro Pack) wird in `marketStats.js` berechnet. Sets, die in fremden Boostern stecken (Classic Collection -> 30th Celebration), stehen in `BOOSTER_OF` und erscheinen in den Analysen nicht als eigene Spalte, sondern zählen zum Booster-Set.

## Offene Punkte
Frontend-Abhängigkeiten (Vite/React Router) auf neue Hauptversionen heben.
